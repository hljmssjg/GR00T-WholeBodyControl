# 真机评估失败日志清单

本文说明真机 VLA 评估日志系统的演进：

1. 官方原始日志系统记录了什么。
2. 原始日志用于失败分析时缺少什么。
3. 本次增加了什么。
4. 最终一次评估会生成什么文件，以及如何使用。

本文以 `outputs/2026-06-01-15-43-01` 为官方原始日志样例。

## 一、官方原始日志系统

官方 `run_data_exporter.py` 在收到 `c` 键后开始或停止录制，将一次
episode 保存成 LeRobot v2.1 数据集。

### 1. 文件结构

原始样例包含：

```text
outputs/2026-06-01-15-43-01/
├── data/chunk-000/episode_000000.parquet
├── videos/chunk-000/observation.images.ego_view/episode_000000.mp4
└── meta/
    ├── info.json
    ├── modality.json
    ├── episodes.jsonl
    ├── episodes_stats.jsonl
    └── tasks.jsonl
```

其中：

| 文件 | 官方记录内容 |
|---|---|
| `episode_*.parquet` | 每帧机器人状态、动作、SONIC/遥操作字段和索引 |
| `episode_*.mp4` | ego 第一视角 RGB 视频 |
| `info.json` | FPS、字段 schema、机器人和模型启动配置 |
| `modality.json` | state、action、video 的字段分组 |
| `episodes.jsonl` | episode 编号、任务文本和长度 |
| `episodes_stats.jsonl` | 每个数值字段的统计量 |
| `tasks.jsonl` | task prompt 及其编号 |

### 2. 官方逐帧记录字段

#### 感知

- `observation.images.ego_view`：ego RGB，640×480，H.264。
- 可选左右腕相机，但原始样例只开启了 ego view。

#### 机器人和 WBC

- `observation.state`：43 维实际关节位置。
- `observation.eef_state`：双腕 FK 位置和四元数姿态。
- `action.wbc`：43 维 WBC 关节目标。
- `action.motion_token`：64 维 SONIC motion token。
- `observation.root_orientation`：base 四元数。
- `observation.projected_gravity`：机体坐标系重力方向。
- `observation.cpp_rotation_offset`、`observation.init_base_quat`：
  C++ 侧朝向初始化信息。

#### SONIC、planner 和遥操作

- `teleop.delta_heading`。
- SMPL joints、pose、body quaternion、目标身体朝向。
- 左右手目标和左右腕目标。
- stream mode、planner mode、移动、朝向、速度和高度。
- VR 三点位置与姿态。

#### 数据集索引

- `timestamp`、`frame_index`、`episode_index`、`index`、`task_index`。

### 3. 官方原始系统能回答什么

它主要面向训练数据采集，可以回答：

- 机器人看到了什么。
- 当前实际关节位置是什么。
- WBC 和 SONIC 收到了什么目标。
- SMPL、VR 或 planner 当时给了什么命令。

因此它适合回放 episode、检查训练字段和分析明显的动作偏差。

### 4. 官方原始系统的失败分析缺口

原始数据不能完整回答以下问题：

- VLA 一次推理用了多久，返回了哪个完整 action chunk。
- chunk 经过 latency compensation 和 resume blend 后，最终发布了哪一帧。
- 机器人没有跟上目标时，是关节速度、力矩、故障还是通信陈旧导致的。
- base/torso 的完整 IMU 加速度和角速度是什么。
- 是否发生 C++ 状态跳帧、相机陈旧或图像与状态错位。
- episode 最终是成功还是失败。
- 操作者何时按下 pause、init、start、stop、success 或 failure。
- 当时运行的是哪个 Git commit、dirty diff 和启动参数。
- C++、inference、exporter 等进程是否打印过异常。

另外，launcher 虽然显示了 `s/f` 操作说明，但原始 exporter 实际只处理
`c/x`，不会把 success/failure 结果写入数据集。

## 二、本次新增日志

目标是让日志可以回答三类问题：

1. VLA 为什么给出这个动作。
2. SONIC/WBC 是否正确执行了动作。
3. 机器人、相机或通信是否让执行结果偏离预期。

### 1. VLA 原生策略 trace

在 `run_vla_inference.py` 中增加原生 sidecar logger，不依赖外部日志包。

记录内容：

- 每次推理的 prompt、耗时和完整原始 action chunk。
- latency compensation 选中的 chunk 起始下标。
- 是否为 resume 后第一个 chunk。
- 每个控制周期最终发布的 motion token 和左右手动作。
- chunk id、chunk 内下标和 resume blend alpha。
- prompt 修改、pause、初始化、控制模式切换等键盘事件。
- action 越界、推理异常和 worker 退出超时。

完整 action chunk 使用压缩 NPZ 保存，逐帧最终动作和事件使用 JSONL 保存。

### 2. 机器人动力学与硬件诊断

C++ `g1_debug` 新增发布、exporter 新增保存：

- 43 维实际关节速度。
- base 和 torso 四元数、角速度、线加速度。
- 29 个电机的绕组/驱动器温度，共 58 维。
- 29 个电机错误码。
- 29 个电机估计力矩。
- encoder mode、motion name 和 play 状态。

这些字段可以直接和 `action.wbc`、`observation.state` 对齐，用于判断：

- 策略目标是否合理。
- WBC 是否生成了合理目标。
- 实际机器人是否跟上目标。
- 跟踪失败是否伴随大速度、大力矩、过温或电机故障。

### 3. 时间同步和丢帧诊断

每帧新增：

- C++ state index 和相邻录制帧的 index delta。
- C++ wall-clock、相机时间戳和 exporter wall-clock。
- state 接收年龄、camera 接收年龄、SONIC pose 年龄。
- 图像与机器人状态的时间差。

其中：

- index delta 大于正常值表示 exporter 中间没有录到某些 C++ 状态。
- age 过大表示当前使用的是陈旧缓存。
- image-state delta 过大表示视觉与机器人状态没有正确对齐。

### 4. Episode outcome 和事件

新增按键语义：

| 按键 | 行为 |
|---|---|
| `c` | 开始录制；录制中再次按下只提示选择 `s/f`，不会保存 |
| `s` | 以 `success` 结果结束 |
| `f` | 以 `failure` 结果结束 |
| `x` | 保存为 discarded |

新增文件：

| 文件 | 内容 |
|---|---|
| `meta/episode_outcomes.jsonl` | episode、task、success/failure/discarded、帧数和起止时间 |
| `meta/events.jsonl` | 按键、episode 开始/停止/保存、motion 切换和异常事件 |

`s/f` 只在 recording 状态生效；非录制状态按下会记录
`episode_stop_ignored`，不会错误保存空 episode。

tmux 每个 pane 顶部有固定标题。右下 data exporter 的标题会持续显示：

- `DATA: IDLE`：等待按 `c`。
- `DATA: RECORDING`：正在录制，并提示 `s/f/x`。
- `DATA: SAVING SUCCESS/FAILURE`：正在编码视频并写入数据。
- `DATA: SAVED SUCCESS/FAILURE`：本条已经真正保存完成。
- `DATA: SAVE ERROR`：保存发生异常，需要检查 `data_exporter.log`。

该标题不会被滚动日志覆盖。按下 `s/f` 后应等待状态从 `SAVING`
变为 `SAVED`，再开始下一条录制。

### 5. 运行环境和控制台日志

launcher 现在保存：

- 完整 launcher 参数和解析后的 config。
- Git commit、`git status` 和完整 dirty diff。
- hostname、Python 版本和启动时间。
- C++ deploy、VLA inference、data exporter、keyboard publisher 和 sim
  的 stdout/stderr。

launcher 也增加了 `--record-wrist-cameras`，在相机服务确实提供左右腕画面时，
可将左右腕视频一起加入 LeRobot 数据集。

## 三、最终日志系统

### 1. 一次评估的输出目录

`launch_inference.py` 使用同一个 `<run>` 名称生成两组目录：

```text
outputs/
├── <run>/
│   ├── data/
│   ├── videos/
│   └── meta/
│       ├── info.json
│       ├── modality.json
│       ├── episodes.jsonl
│       ├── episodes_stats.jsonl
│       ├── tasks.jsonl
│       ├── episode_outcomes.jsonl
│       └── events.jsonl
└── <run>-process-logs/
    ├── run_manifest.json
    ├── git_status.txt
    ├── git_diff.patch
    ├── cpp_deploy.log
    ├── vla_inference.log
    ├── data_exporter.log
    ├── keyboard_publisher.log
    ├── sim.log
    └── inference_trace/
        ├── session.json
        ├── events.jsonl
        ├── published_actions.jsonl
        └── chunks/
            ├── chunk_000000.npz
            └── ...
```

真机模式没有 `sim.log`；不开腕相机时只有 ego 视频。

### 2. 最终覆盖的完整链路

| 阶段 | 最终可查看的数据 |
|---|---|
| 任务输入 | 初始 prompt、运行时 prompt 修改、task index |
| 视觉输入 | ego RGB，可选左右腕 RGB，采集时间和数据年龄 |
| VLA 原始输出 | 完整 action chunk、推理耗时、chunk id |
| 动作处理 | latency compensation 起始下标、resume blend alpha |
| 实际发布 | 每帧 token、双手动作、frame index |
| SONIC/WBC | motion token、WBC 关节目标、模式和参考 motion |
| 机器人响应 | 关节位置/速度、双手状态、base/torso IMU |
| 硬件状态 | 电机温度、错误码和估计力矩 |
| 通信质量 | state index delta、各数据年龄、image-state delta |
| 运行环境 | 模型配置、Git 状态、启动参数和各进程日志 |
| 评估结果 | success、failure、unknown 或 discarded |

### 3. 失败分析目标

最终日志应能区分：

- **策略失败**：VLA 原始 chunk 已经做出了错误决策。
- **时延失败**：推理过慢、起始下标跳过过多或输入数据陈旧。
- **控制失败**：VLA 目标合理，但 WBC 目标或实际关节跟踪异常。
- **硬件失败**：出现过温、电机错误、大力矩、碰撞或失稳。
- **感知失败**：目标不可见、图像陈旧或图像与状态不同步。
- **系统失败**：某个进程异常退出、ZMQ 中断或配置与预期不一致。

## 四、仍建议补充

以下数据当前链路没有可靠来源，不能靠 exporter 凭空补出。

### P0：失败定位价值最高

- 外部第三视角视频。ego 画面常看不到脚、碰撞、身体与桌沿关系。
- 手部接触信号。至少需要夹爪电流/力矩；最好有触觉或指尖力。
- 足底接触/力。用于区分策略失衡、打滑和 WBC 跟踪失败。
- PolicyServer 内部耗时分解：图像预处理、网络前向、后处理、排队时间。
- 精确统一时钟。PC、G1、相机服务器应做 PTP/NTP，并记录 clock offset。

### P1：复现和长期统计

- 深度图或点云，以及相机内参、外参、畸变参数和标定版本。
- CPU/GPU 利用率、显存、温度、系统负载和磁盘写入延迟。
- ZMQ 每路消息的发送序号、发送时间、接收时间、丢包/覆盖计数。
- 电池电压、电流、SOC，以及保护/急停状态。
- Python lockfile、容器镜像、ONNX/checkpoint 哈希。
- 场景元数据：桌高、物体初始位姿、光照、机器人初始位姿。

### P2：便于 agent 自动分析

- 失败 taxonomy，例如 `navigation`, `reach`, `grasp`, `lift`,
  `collision`, `timeout`, `operator_abort`, `system_error`。
- 关键时刻人工标注，例如“首次看到目标”“首次接触”“抓稳”“物体掉落”。
- 自动派生指标：关节跟踪误差、动作平滑度、最大倾角、最大温度、
  推理延迟 P50/P95/P99、相机/状态 stale 比例。

## 五、推荐判断顺序

分析 failure 时先看：

1. outcome 和外部视频，确认失败发生在哪个阶段。
2. `-process-logs/inference_trace`，判断 VLA 原始动作是否已经错误或延迟。
3. `action.wbc - observation.state`、速度和力矩，判断 WBC/硬件是否未跟上。
4. age、index delta、process logs，排查相机、状态、ZMQ 和进程异常。
5. 温度、错误码、姿态和加速度，排查保护、碰撞和失稳。
